# Tasks: Задачи следующего этапа UX-прототипа

Это задачи создания и проверки UX-артефактов, а не полный implementation backlog работающего приложения. Продуктовые приоритеты B01–B12 находятся в `docs/ux/astra-priorities.md`; техническая реализация планируется отдельно после выбора стека.

**Input**: `specs/002-senior-mobile-ux/spec.md`, `plan.md`; `docs/ux/luna-research.md`, `astra-priorities.md`, `platform-check.md`, `evidence-check.md`.

**Prerequisites**: Спецификация и план прочитаны; семейные аккаунты, телефонная служба, бюджет и бизнес-пилот не входят в обязательный объём. Дизайн A — рабочая рекомендация, стек не выбран.

**Tests**: Проверки сценариев и доступности заданы спецификацией. Здесь создаются UX-артефакты и протоколы; автоматизированные тесты приложения, реальные пользовательские сессии и проверка на устройствах не выдаются за выполненные.

**Organization**: Фазы сгруппированы по пользовательским историям. P0/P1 — приоритет истории; `[P]` — допустимость независимой работы с файлами, не команда запускать агентов. Все задачи ниже запланированы и не выполнены.

## Format: `[ID] [P?] [Story] Description`

- ID последовательно от T001 до T023.
- `[P]` означает разные файлы без зависимости между задачами одного указанного набора после выполнения их предпосылок.
- `[US1]`, `[US3]`, `[US2]` соответствуют историям в спецификации; US3 стоит раньше US2 из-за приоритета P0.
- В каждой задаче указан точный путь относительно корня проекта и проверяемый результат.

## Path Conventions

Все UX-артефакты — в `docs/ux/prototype/`. SVG — редактируемые схемы с именованными экранами/состояниями, Markdown — переходы и проходы, CSV — строки. Мобильные каталоги/API/зависимости не создаются. Техническое решение до реализации — `specs/002-senior-mobile-ux/technology-decision.md`.

## Phase 1: Setup (Shared Infrastructure)

**Purpose**: Подготовить индекс демонстрационного комплекта без установки стека.

- [ ] T001 Создать `docs/ux/prototype/README.md`: перечислить входные документы, будущие файлы и границу «демонстрация, услуги не заказываются»; приёмка — отдельно названы готовые и только планируемые артефакты, нет заявления о runtime-проверках.

## Phase 2: Foundational (Blocking Prerequisites)

**Purpose**: Зафиксировать общие правила до проектирования историй. Зависит от T001.

- [ ] T002 Описать в `docs/ux/prototype/screen-map.md` три постоянных раздела и пути US1/US3/US2, просмотр без входа, возврат и контекстный вход; приёмка — у каждого экрана назначение, вход и выход, помощь с приложением отделена от бытовой помощи.
- [ ] T003 [P] Подготовить `docs/ux/prototype/accessibility.md` после T002: Android ≥48×48 dp, sp/системный масштаб; iOS проектные ≥48×48 pt/Dynamic Type; контраст, роли, фокус, объявления и переносы; приёмка — определены проверки максимального системного текста и дикторов отдельно на обеих платформах, макет не назван их доказательством.
- [ ] T004 [P] Подготовить `docs/ux/prototype/content-ru-kz.csv` после T002 с ID, контекстом, RU, KZ, статусом редакторской проверки и комментарием; включить меню, согласия, ошибки, статусы и честные метки демонстрации; приёмка — нет пустого неотмеченного перевода и утверждения, что автоматический перевод проверен носителем.
- [ ] T005 [P] Описать в `docs/ux/prototype/shared-states.md` после T002 переходы загрузки, черновика, отправки, неизвестного результата, подтверждения, старых данных, отмены, ошибки входа и отказа в разрешениях; приёмка — у каждого состояния текст, доступное действие и основание перехода, повтор после потери ответа сначала проверяет существующую операцию.

**Checkpoint**: T001–T005 завершены; есть согласованные правила, на которых истории могут проектироваться независимо.

## Phase 3: User Story 1 - Бытовая помощь (Priority: P0)

**Goal**: Законченное первое сечение помощи с исправлением, статусом и отменой. Зависит от Phase 2.

**Independent Test**: Пройти демонстрационный запрос от открытого просмотра до отмены; отдельно потерять ответ на отправку. Проверяется логика экранов; будущая серверная защита от дублей отмечается как непроверенная.

### Implementation for User Story 1 — UX-артефакты

- [ ] T006 [US1] Создать `docs/ux/prototype/home.svg` по варианту A: две подписанные задачи, язык, условный блок черновика, помощь и постоянные разделы; приёмка — есть обычный и крупный текст, длинные подписи не перекрываются, демонстрационная метка видима.
- [ ] T007 [US1] Описать `docs/ux/prototype/help-flow.md` после T006: условия → район/время → необходимый вход → резюме → статус → отмена/проблема; приёмка — зафиксированы все US1 acceptance scenarios, адрес передаётся только после осознанного согласия с конкретным предложением, неизвестная цена/проверка не скрывается.
- [ ] T008 [P] [US1] Создать `docs/ux/prototype/help-screens.svg` после T007 с условиями, полями, резюме, исполнителем и подтверждённым статусом; приёмка — обычный/крупный текст, RU/KZ контент из словаря, видимые изменение/назад, никакой вымышленной реальной проверки.
- [ ] T009 [P] [US1] Создать `docs/ux/prototype/help-recovery.svg` после T007: ошибка поля, пустое покрытие, черновик, неизвестный результат, старый статус, отмена ожидается и проблема; приёмка — у каждого экрана следующий шаг, ошибка не стирает форму, неизвестный результат не изображает успех/отказ.
- [ ] T010 [US1] Подготовить `docs/ux/prototype/help-walkthrough.md` после T008–T009 с ссылками на экраны и проходами US1; приёмка — для каждого критерия указаны вход, действие, ожидаемое состояние, фактический результат ревью и ограничения проверки макета.

**Checkpoint**: История проверяется на синтетическом запросе; US3 затем добавляет постоянный вход в этот запрос из общего раздела.

## Phase 4: User Story 3 - Вернуться и разобраться (Priority: P0)

**Goal**: Найти свои действия, понять актуальность, сменить язык и получить инструкции. Зависит от Phase 2; самостоятельный пример не требует выполнения US1.

**Independent Test**: Открыть заранее заданное обращение после перерыва, увидеть старый статус при отсутствии сети, сменить язык, восстановиться после ошибки входа; доступность аннотирована, runtime ещё не проверен.

### Implementation for User Story 3 — UX-артефакты

- [ ] T011 [US3] Описать `docs/ux/prototype/return-flow.md`: заполненный/пустой список, возврат к статусу, язык, вход и инструкции; приёмка — покрыты все US3 acceptance scenarios, определён синтетический пример для независимой проверки, нет зависимости от push.
- [ ] T012 [P] [US3] Создать `docs/ux/prototype/my-requests.svg` после T011 со списком заявок/записей, пустым состоянием и временем обновления; приёмка — видны вид обращения, дата, статус и следующее действие, личные данные не появляются в публичном просмотре.
- [ ] T013 [P] [US3] Создать `docs/ux/prototype/app-help.svg` после T011 с языком, инструкциями, контекстным входом/восстановлением и состоянием отсутствующей живой поддержки; приёмка — отказ от разрешений не тупик, смена языка сохраняет ввод, нет фиктивного оператора.
- [ ] T014 [US3] Подготовить `docs/ux/prototype/return-walkthrough.md` после T012–T013 с независимым примером и проверкой всех US3 acceptance scenarios; приёмка — у каждого результата есть экран/переход, будущая проверка дикторов и сохранения после перезапуска выделена отдельно.

**Checkpoint**: US1 + US3 составляют рекомендуемое первое вертикальное сечение, без обязательных семейных ролей и телефонного канала.

## Phase 5: User Story 2 - Встречи (Priority: P1)

**Goal**: Независимая запись на встречу и отмена. Зависит от Phase 2; использует общий паттерн статуса без обязательного прохождения US1.

**Independent Test**: На отдельном синтетическом событии записаться, вернуться к записи и отменить; дополнительно проверить полную группу, перенос времени и отмену организатором.

### Implementation for User Story 2 — UX-артефакты

- [ ] T015 [US2] Описать `docs/ux/prototype/meetings-flow.md` для просмотра, подробностей, записи, возврата и отмены; приёмка — все US2 acceptance scenarios, дата/место/язык/стоимость/доступность до записи и новый выбор при переносе, нет автоматической зависимости от заказа помощи.

**Checkpoint**: Все три истории имеют самостоятельные демонстрационные проходы.

## Dependencies & Execution Order

### Phase Dependencies

```text
T001 → T002 → (T003, T004, T005)
                    ├→ US1: T006 → T007 → (T008, T009) → T010
                    ├→ US3: T011 → (T012, T013) → T014
                    └→ US2: T015 → (T016, T017) → T018
T010 + T014 + T018 → T019 → (T020, T021, T022) → T023
```

Порядок по приоритету: общие правила → US1 → US3 → US2 → общий разбор. Три истории можно проектировать независимо после Phase 2; при изменении общего правила сначала обновить его, затем зависимые схемы. Словарь T004 — исходный; полное согласование со всеми экранами — T020.

### User Story Dependencies

- US1 использует общие правила; для самостоятельного прохода достаточно локального экрана статуса.
- US3 использует подготовленную синтетическую запись; при интеграции после T010/T014 проверяется возврат к конкретному запросу US1.
- US2 использует синтетическое событие; при интеграции после T014/T018 проверяется появление записи в общем списке.
- Начало кода требует принятого технического решения и отдельного плана реализации. Результат T022 «не принято» не блокирует документирование handoff, но блокирует код.

### Parallel Opportunities

Только после предпосылок: T003/T004/T005; T008/T009; T012/T013; T016/T017; T020/T021. T022 также может исследоваться отдельно после T019, но не определяет стек молча.

## Implementation Strategy

### MVP First

T001–T014 дают первое вертикальное сечение помощи и возвращения к ней. Перед его демонстрацией требуется соответствующая часть проверки T019 и честная маркировка. Это UX-MVP, не запущенная услуга. Доступность, язык и ошибки входят в него с начала.

### Incremental Delivery

Затем T015–T018 добавляют встречи; T019–T023 сводят качество, протокол проверки и технические решения. P2 не реализуется автоматически. Наличие плана не означает разрешения публиковать приложения или запускать услуги.
